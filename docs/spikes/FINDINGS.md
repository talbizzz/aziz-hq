## S1: Does headless `claude -p` expose usage / rate limits?
- **Verdict:** CONFIRMED WITH CHANGES (the signal exists, but in a different place than assumed)
- **Evidence:** [version](evidence/S1-version.txt), [json output](evidence/S1-a-json.json), [stream output](evidence/S1-a-stream.jsonl), [headless statusLine dump (empty)](evidence/S1-b-statusline-headless.jsonl), [usage vs /usage](evidence/S1-d-usage-compare.md), [calibration](evidence/S1-d-calibration.jsonl), [isolated auth](evidence/S1-e-isolated-auth-status.txt), [isolated headless](evidence/S1-e-isolated-headless.txt)
- **What we learned:**
  - `--output-format json` returns token counts (`usage`, `modelUsage`) and `total_cost_usd`, but **no** rate-limit fields.
  - `--output-format stream-json --verbose` emits a `rate_limit_event` per call: `rate_limit_info.unifiedWindows.{five_hour,seven_day}` each with `utilization` (fraction, 0.02 = 2%), `resetsAt` (unix seconds) and `status` (`allowed`, ...). It also has `overageStatus`/`isUsingOverage`.
  - Matches interactive `/usage`: reset times identical; percentages equal within ±1pp (weekly 0.09 vs 10%).
  - The event reflects state **before** the call; the effect of a call shows in the next call's event.
  - Resolution is 1%. Six calls (~$0.45 list cost) moved 5h from 0.02 to 0.04, so per-call token calibration is too coarse to be useful; the real percentage is available directly.
  - A `statusLine` command is **never** invoked in headless mode (dump file stayed empty), so `rate_limits` via statusLine is not an option headless.
  - `CLAUDE_CONFIG_DIR=<dir>` isolation works after a separate `claude auth login`: `auth status` is logged in, headless calls succeed, sessions are written under `<dir>/projects`, the default config is unaffected. **Quota is per account, not per config dir**: the isolated call showed the same shared 5h/weekly utilization.
  - Each `claude -p` call carries ~38k tokens of baseline context (cache create + read), costing ~$0.06 list even for "Reply with OK".
- **Decision for the plan:** Usage policy (M4) uses the `rate_limit_event` from `stream-json` as the primary source; the worker runs `claude -p --output-format stream-json --verbose`. Fallback if the event is missing: cost-based estimate (`total_cost_usd`) plus limit-error detection (S5). Use `CLAUDE_CONFIG_DIR` to give the worker its own login/session state; it does not give it separate quota. Project-Plan pre-mortem #2 and the M4 stub should say this (applied in T0.7).
- **Open follow-ups:** The event schema is undocumented and may change between versions: pin/record the `claude` version and treat a missing event as a warning (M4). Check whether the event is emitted when the 5h window is near full or blocked (S5, T0.3).

## S5: What does `claude -p` do when a plan limit is hit mid-task?
- **Verdict:** CONFIRMED WITH CHANGES (detection design confirmed against documentation only; the live limit-hit test was declined by Aziz on 2026-11-02 and is **unverified**)
- **Evidence:** [documented fixtures](evidence/) `S5-fixture-*.txt` (all marked DOCUMENTED, none captured live, except `S5-fixture-ok-stream.txt` which has the real S1 event shape); classifier and tests in `spikes/s5/` (10 tests passing).
- **What we learned:**
  - Official docs (code.claude.com headless + errors): exit 0 on success, non-zero on failure, but failures *inside* a run (e.g. missing auth) are printed as the `result` on stdout. A community bug report (claudeissues.com #79500) says rate-limit errors can come back as `subtype:"success"`, `is_error:true`, **exit 0**. So the exit code alone must not be trusted.
  - Documented messages: `You've hit your session limit` / `weekly limit` / `Opus limit` / `Sonnet limit`; `Request rejected (429)`; `Server is temporarily limiting requests`. Auth: `Not logged in · Please run /login`, `Login expired`, `OAuth token revoked/has expired`, account on hold.
  - Streaming exposes `system/api_retry` events (`error` category incl. `rate_limit`, `authentication_failed`, `billing_error`; `error_status`). Temporary 429s are retried internally (up to 10); spend-limit 429s are not.
  - `rate_limit_event.rate_limit_info` has `status` (`allowed` observed in S1) and per-window `status` and `resetsAt`: the reset-time source. The value used for a *blocked* window is assumed (`rejected`); the classifier treats any status other than `allowed` as a limit.
  - SIGTERM exits 143 and records no result for the in-flight turn; started Bash commands are killed. Files already written stay on disk, so a worktree can be left dirty: the runner must assume this.
  - Classifier `classifyClaudeFailure(exitCode, stdout, stderr) -> 'limit' | 'auth' | 'other'` uses: any non-allowed `rate_limit_event` window, else (non-zero exit OR `is_error:true`) AND text matching the pattern lists. Unknown failures return `other`.
- **Decision for the plan:** M4's runner uses `stream-json`, classifies with this function (pattern lists configurable), and on `limit` pauses until `resetsAt` (from the event) or, if absent, 30 min; on repeated unknown failures (N tries) treat as "possible limit" and pause 30 min rather than fail the task. Before pausing/retrying, the runner resets or discards the task worktree to the last commit. **Before M8**, run one live limit-hit capture (Aziz's go-ahead, sleeping hours) and replace the DOCUMENTED fixtures with real ones.
- **Open follow-ups:** Live capture of the real blocked-state event/exit code/message and of the call during and after the blocked period (owner: M4 detailing or M8 start). Mid-task kill behaviour with a real limit.

## S2: Can a per-task Docker sandbox run `supabase start`, tests and `git push`?
- **Verdict:** CONFIRMED WITH CHANGES (macOS/Colima leg only; Linux/VPS leg re-run at M8 start)
- **Evidence:** [measurements](evidence/S2-measurements.md), [check.sh result (A, 3 parallel)](evidence/S2-check-A.txt), [topology B run](evidence/S2-topology-B.txt), [allowlist proxy](evidence/S2-allowlist-proxy.txt); code in `spikes/s2/` (`Dockerfile`, `sandbox.sh`, `sandbox-b.sh`, `check.sh`, `proxy/`).
- **What we learned:**
  - Both topologies work. A (sibling containers via `docker.sock`): cold 14m44s, warm **20 s**, ~750 MiB RAM per slim stack, 3 parallel stacks ~2.0 GiB, shared 5.7 GB image cache. B (DinD): cold 8m08s *every time* (no shared cache), 1.3 GiB per sandbox, 4.6 GB disk per sandbox.
  - Slim stack (`-x studio,imgproxy,edge-runtime,logflare,vector,mailpit,supavisor`) is enough for `db reset`, `supabase test db` (pgTAP) and auth/rest/realtime/storage. `check.sh` passes 12/12 for 3 parallel A sandboxes; each runs status, pgTAP and `git push` (to a local bare remote; push to GitHub with real credentials is untested).
  - **Security:** A as written puts `docker.sock` inside the agent's container = root on the daemon, defeating the sandbox. B needs `--privileged`. Neither is acceptable for untrusted agent code as-is.
  - **Variant A-prime works:** the *worker* starts the stack (it holds the socket); the agent container has no socket, joins `supabase_network_<project_id>`, and reaches Postgres (`supabase_db_<id>:5432`) and Kong (`:8000`). `docker update --memory/--cpus` caps the Supabase containers (limits on the agent container alone do not cover siblings).
  - Port scheme: `project_id = s2slot<N>`, every `543xx` port + 100*N. Collision failure: `Bind for 0.0.0.0:54322 failed: port is already allocated`. `inspector_port` (8083) must also be shifted if edge-runtime is enabled.
  - Worktree is mounted at the identical absolute path on host, VM and container.
  - Teardown (`supabase stop --no-backup`, `docker rm`) leaves nothing for A. For B, `docker rm -v` is required or anonymous volumes leak.
  - Allowlist: `--internal` Docker network + tinyproxy sidecar with domain allowlist works (github/npm/anthropic reachable, others blocked, direct egress fails). It governs only the agent container; the Supabase stack pulls images through the host daemon, so registry access is the host's concern.
  - Environment gotcha: the Colima default VM here is 2 CPU / 2 GiB, too small; S2 used a separate profile `s2` (4 CPU / 5 GiB), stopped but kept (images cached). `colima start` switches the docker context.
- **Decision for the plan:** M4 uses **A-prime**: worker-managed slim Supabase stack per task (ports base + 100*slot, unique `project_id`), agent container without `docker.sock`, on the stack network, with the egress proxy; worker applies `docker update` limits to the stack and tears it down (`supabase stop --no-backup`, `docker rm -v`, network removal). Pre-pull images on the worker host. Budget for netcup (4 vCore / 8 GB): about 0.75 GiB idle per stack plus the agent, so **2 parallel tasks, 3 at most**, leaving room for the worker and OS (peak RAM during `db reset` / test load was not measured). Add this to the M4 stub, and a repeat of `spikes/s2/check.sh` on the VPS at the start of M8.
- **Fallback (pre-mortem #7):** not needed. If A-prime fails on Linux, use B with a pre-baked dind image or a registry pull-through cache.
- **Open follow-ups:** (1) Peak RAM under load and minimum `--memory/--cpus` that still pass (M4). (2) A-prime agent-container egress when it must also reach the Supabase network and the proxy (M4). (3) Real `git push` to GitHub with a deploy credential (M4). (4) Linux verification (M8). (5) Supabase CLI version skew: host 2.109.1 vs sandbox npm `supabase` 3.0.0; pin a version in the worker image (M4).

## S3: Vite SPA on Cloudflare Pages + Supabase Auth MFA + Cloudflare Access (ADR-12)
- **Verdict:** CONFIRMED WITH CHANGES. **ADR-12 (SPA on Pages) is CONFIRMED** for everything testable without Cloudflare (local `wrangler pages dev` in workerd + local Supabase). **UNVERIFIED** (needs Aziz's Cloudflare credentials, not provided): `wrangler pages deploy`, DNS `spike-hq.aziztalbi.com`, Access application/redirect, real JWKS and AUD, `pages.dev`/preview URLs on a live account, Workers Free CPU limit in production.
- **Process note:** the first S3 run was built against the older plan (Next.js + OpenNext on Workers) because the planning files changed between my first read and the first commit. It was kept as the comparison variant (`spikes/s3-opennext/`, evidence `S3-opennext-*`) and S3 was then redone for the current spec in `spikes/s3/`.
- **Evidence:** [Playwright run (SPA + Pages Functions)](evidence/S3-playwright.txt), [sizes](evidence/S3-spa-bundle-size.txt), [Vite build](evidence/S3-spa-build.txt); comparison variant: [OpenNext bundle size](evidence/S3-opennext-bundle-size.txt), [OpenNext Playwright](evidence/S3-opennext-playwright.txt), [OpenNext extra checks (RLS aal1/aal2, websocket target)](evidence/S3-opennext-extra-checks.txt), [OpenNext build](evidence/S3-opennext-build.txt) ([edge middleware](evidence/S3-opennext-build-edge-middleware.txt), [node proxy](evidence/S3-opennext-build-node-proxy.txt)).
- **Versions:** vite 8.3.5, react-router-dom 7.18.5, @supabase/supabase-js 2.118.0, jose 6.2.15, grammy 1.46.0, wrangler 4.156.1, otplib 13.6.0, Playwright 1.64.1, Node 24.9.0, pnpm 11.21.0, Supabase CLI 2.109.1 (local lean stack: db, auth, rest, realtime, kong). OpenNext variant: next 16.4.3, @opennextjs/cloudflare 1.20.15.
- **What we learned:**
  - **Sizes:** SPA JS 476 kB raw / **138 kB gzip**. Pages Functions bundle (Access middleware with `jose`, `/api/ping`, Telegram webhook with `grammy/web`) **46 kB gzip**: about 65x under the Workers Free 3 MB limit. The OpenNext variant needs 1.13-1.36 MB gzip.
  - **Pages config that worked:** `wrangler.jsonc` with `pages_build_output_dir: dist`, `compatibility_flags: ["nodejs_compat"]`, `compatibility_date 2026-10-01`, `vars.ENVIRONMENT = "production"`; `public/_routes.json` = `{"version":1,"include":["/*"],"exclude":[]}`; `public/_redirects` = `/* /index.html 200`.
  - **Checks passing (5/5, Playwright, local workerd):** unauthenticated `/`, `/dashboard`, `/mfa` redirect to `/login` (SPA guard); login forces `/mfa`; aal1 cannot open `/dashboard`; TOTP enroll+verify (otplib) reaches the dashboard at **aal2**; Realtime insert shows up (828 ms measured end to end including polling; 37 ms in the OpenNext run); session in browser storage survives a refresh, is shared by a second tab, and sign-out in tab 1 sends tab 2 to `/login` on reload.
  - **Access middleware (ADR-10) verified with a test keypair/JWKS:** with `_routes.json` including `/*` the middleware runs for **static assets and SPA fallback routes** too: `/`, `/index.html`, `/_redirects`, `/dashboard`, a hashed JS asset all return 403 without a token and 200 with a valid one; wrong audience, garbage and **expired** tokens return 403.
  - **Fail closed:** the Workers runtime has no `NODE_ENV`, so use an explicit `ENVIRONMENT` var (`production` in `wrangler.jsonc`, overridden to `development` only for local dev). Unset `CF_ACCESS_*` with `ENVIRONMENT=production` returns 500 for every route.
  - **ADR-1 at the data layer** (verified in the OpenNext run against the same migration): with RLS `auth.jwt()->>'aal' = 'aal2'`, an aal1 session reads 0 rows, an aal2 session reads all 6.
  - **Realtime:** the browser WebSocket goes straight to Supabase (`/realtime/v1/websocket`), not through Cloudflare (captured from the browser). Gotcha: `SUBSCRIBED` fires on the join reply but `postgres_changes` becomes active a moment later ("Subscribed to PostgreSQL" system message); rows inserted in that gap are never delivered, so the dashboard must refetch after subscribing (fits ADR-9 query invalidation). Set the Realtime token (`realtime.setAuth(access_token)`) before subscribing.
  - **Other gotchas for M1:** (1) the MFA page must remove stale *unverified* TOTP factors before `enroll` (else `mfa_factor_name_conflict`); (2) on this Supabase version new `public` tables get **no default grants** for API roles: grant explicitly (M1 C-contract already does); (3) `sb_secret_` keys are not JWTs: send as `apikey` only, never as `Authorization: Bearer`; (4) otplib 13 has no `authenticator`: use `generate({secret})`; (5) pnpm 11 needs `allowBuilds` (esbuild, workerd) via `pnpm approve-builds`; (6) concurrent `wrangler pages dev` instances need distinct `--inspector-port` values; (7) `supabase start` pulls the edge-runtime image even with `-x edge-runtime` during `db reset`; it was harmless here (disabled in config).
  - **Comparison variant (OpenNext):** builds Next 16 in 14 s and passes the equivalent checks; edge `middleware.ts` works, `proxy.ts` works but OpenNext marks Node middleware experimental. Not needed since no blocker was found in the SPA.
  - **CPU time per request on Workers Free (10 ms)** cannot be measured locally and remains unverified; the Functions code is a JWT verification plus (webhook only) two fetches, so headroom is likely but not proven.
- **Decision for the plan:** ADR-12 stands: SPA on Pages, Pages Functions for the Access middleware and `/api/health`. Update ADR-10 to use an explicit `ENVIRONMENT` variable instead of `NODE_ENV`; keep `_routes.json` with `/*`. Add the gotchas above to M1 T1.10 (MFA page factor cleanup, Realtime auth/refetch), T1.11 (flags). The OpenNext variant stays a documented fallback only.
- **Open follow-ups (need Aziz):** deploy `spikes/s3` with `wrangler pages deploy`, create the Access app, and re-run `check.spec.ts` against the deployed URL (redirect, real JWT/AUD, `pages.dev` and preview URLs, Free CPU). Owner: M1 T1.11 with those checks in its smoke script.

## S4: Can a gate be answered from Telegram inline buttons through a secure webhook?
- **Verdict:** CONFIRMED WITH CHANGES for the handler logic, both hosting variants and idempotency (all verified locally with a mock Telegram Bot API). **UNVERIFIED** (needs Aziz: a BotFather bot, Cloudflare and a hosted Supabase project): real `setWebhook`, Telegram actually reaching the endpoint, the Access bypass policy on a live account, real press-to-edit latency, a hosted Edge Function deployment.
- **Evidence:** [unit tests (10 passing)](evidence/S4-unit-tests.txt), [idempotency SQL](evidence/S4-idempotency-sql.txt), [Edge Function (Deno) check](evidence/S4-edge-function-check.txt), [Pages Function checks (in the S3 run, test 7)](evidence/S3-playwright.txt); code in `spikes/s4/` (`webhook.ts`, `webhook.test.ts`, `edge/`) and `spikes/s3/functions/api/telegram/webhook.ts`.
- **Versions:** grammy 1.46.0, Vitest 5.0.5, Deno 2.9.6 (from npm, temp directory).
- **What we learned:**
  - **Security rules verified** (unit tests, Pages Function in workerd, Deno): missing or wrong `X-Telegram-Bot-Api-Secret-Token` -> 401, no store write, no Telegram call; another user, or the owner in another chat -> 200, ignored and logged, no side effect; malformed callback data ignored. grammY's `webhookCallback(bot, "std/http", { secretToken })` does the header check.
  - **Callback data:** `g:<32-hex gate uuid>:<a|m|d>` = 36 bytes (limit 64), strict regex parser, round trip tested.
  - **Idempotency:** decision table with `UNIQUE(gate_id)`; with real Postgres `insert ... on conflict (gate_id) do nothing returning decision` returns 1 row for the first press and 0 for the second; the handler answers "Already decided: X" and edits the message.
  - **Flow:** press -> `callback_query` -> decide -> `answerCallbackQuery` + `editMessageText` (both called).
  - **Access bypass (Pages Function variant):** the middleware skips only `/api/telegram/webhook`; with Access enforced, that path reaches the handler without an Access header while `/api/ping`, `/`, `/index.html`, `/api/telegram` and `/api/telegram/webhook/x` all return 403. The Cloudflare-side bypass policy itself (path-scoped Access application) is **UNVERIFIED**.
  - **Runtime gotchas:** `import "grammy"` (Node entry) fails inside workerd with `Expected signal to be an instanceof AbortSignal`; use `import "grammy/web"`. Pass `botInfo` to skip `getMe` on cold start. `webhookCallback` already supports Deno/Edge (`std/http`).
  - **Latency:** handler plus 2 mock Telegram calls: 7-13 ms (Worker and Deno). Real press-to-edit latency was **not measured**.

| | Pages Function | Supabase Edge Function |
|---|---|---|
| Setup effort | none extra: ships with the dashboard deploy | separate deploy with the Supabase CLI; must be deployed with `verify_jwt = false` (Telegram sends no Supabase JWT) |
| Where the service-role key lives | Cloudflare Pages secrets (new place for the key) | inside Supabase (injected into the function); never leaves the platform |
| Access bypass needed | yes: a path-scoped bypass app in Cloudflare Access (one more hole to get right) | none: it is not behind Access |
| Cold start | workerd, ms | 68 ms locally with a warm cache (Deno); hosted cold start UNMEASURED |
| Local testability | `wrangler pages dev` works (tested) | Deno works (tested); `supabase functions serve` could not run here (edge-runtime image pull failed in the Colima VM) |
| Runs on Free | yes | yes (hosted limits UNVERIFIED) |

- **Decision for the plan (ADR-5, picks one as the spike requires):** use the **Supabase Edge Function** for the webhook. Reason: it keeps the service-role key inside Supabase and removes the Cloudflare Access bypass, the single most security-sensitive configuration. Shared code stays in `packages/core` (secret check, owner check, callback parse, decision logic with an injected store; `grammy/web`). The Pages Function variant is proven and is the documented fallback if the hosted Edge Function misbehaves; the dashboard middleware then skips only `/api/telegram/webhook` as tested. Aziz confirms this pick at the M0 go/no-go.
- **Open follow-ups (need Aziz):** create the bot; deploy the function to the hosted project with `verify_jwt = false`; run `setWebhook` (`secret_token`, `allowed_updates=["callback_query","message"]`); measure real latency and cold start; confirm Telegram reaches it. Owner: M3 (Telegram buttons), after M1 T1.9 creates the hosted project.
